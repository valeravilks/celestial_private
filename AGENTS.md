# Работа с архитектурными решениями

После добавления ADR или изменения его статуса проверяй результат и создавай локальный Git-коммит с ADR и связанными изменениями задачи. Проверяй состав индекса; добавляй файлы явно, не захватывай несвязанные изменения пользователя и приватные материалы. Несколько связанных ADR одной задачи можно сохранять одним коммитом. Не выполняй push без отдельного указания. При невозможности коммита сообщи причину. Основание: `docs/adr/0016-commit-adr-changes.md`.

Самостоятельно разделяй запрос пользователя на отдельные ADR по независимым решениям, даже если они изложены одним сообщением. Решения, которые можно пересмотреть отдельно, оформляй отдельно; тесно связанные детали одного решения (например, пути каталогов и их назначение) объединяй. Не создавай ADR на каждую мелкую деталь. Основание: `docs/adr/0007-split-independent-decisions.md`.

Перед планированием и внесением изменений прочитай реестр `docs/adr/README.md` и действующие ADR, относящиеся к задаче. Заменённые ADR используй как исторический контекст, а не как действующие требования.

Сопоставь запрос пользователя и предлагаемые изменения с действующими решениями. Если обнаружено противоречие:

1. До замены ADR или реализации противоречащих изменений сообщи пользователю номера и названия затронутых ADR, существующие требования и суть противоречия.
2. Объясни предлагаемую замену и её последствия. По возможности предложи вариант, совместимый с текущими решениями.
3. Дождись явного подтверждения пользователя на замену конкретных решений. Общий запрос на новую функциональность сам по себе не означает согласия на пересмотр ADR. Если такое подтверждение уже получено после объяснения противоречия, повторно его не запрашивай.
4. После подтверждения оформи новый ADR, свяжи его с заменяемыми записями и обнови их статусы и реестр. Сохрани исходный контекст и текст прежних решений.

До подтверждения можно подготовить предложение со статусом «Предложено» и продолжать независимую работу, совместимую с действующими ADR. Изменения без противоречий выполняй без дополнительного согласования.

Основание: `docs/adr/0005-review-existing-decisions-before-replacement.md`.

# Поддержание описания архитектуры

Используй `docs/architecture.md` для обзора текущей архитектуры, проверяя относящиеся к задаче действующие ADR. При принятии или замене ADR и при изменении состояния реализации обновляй затронутые разделы этого документа. Различай выбранное, реализованное и ещё не определённое. Причины и историю решений сохраняй в ADR; версии и настройки бери из конфигураций проекта, когда они появятся. Основание: `docs/adr/0006-document-current-architecture.md`.

# Граница передачи клиенту

Тема `wordpress/theme/` — основная FSE-тема Celestial для внешнего представления. Добавляй в неё только необходимое для оформления и работы FSE-темы. Не вводи сборку темы (в том числе из корня проекта), сборочные зависимости и генерируемые `build/` или `dist/`. Файлы темы используются WordPress напрямую. Функциональность, сохраняемая при смене темы, относится к плагину. Способ сборки плагина этим правилом не определяется. Основание: `docs/adr/0013-fse-theme-without-build.md`.

Вся разработка сайта ведётся внутри `wordpress/`. В корне этого каталога сохраняй `.wp-env.json`, компоненты и самостоятельную документацию. Не создавай там `package.json`, lock-файл, `.nvmrc` или локальные npm-зависимости. wp-env устанавливай глобально и запускай прямыми командами из `wordpress/`.

Будущие npm-конфигурацию, `.nvmrc` и зависимости плагина размещай в `wordpress/plugin/` после определения способа его разработки. Сейчас эти инструменты ещё не выбраны. У темы сборки нет.

Внутренние ADR, описание архитектуры, правила и приватные заметки процесса Celestial храни вне этого каталога. Документация внутри `wordpress/` должна быть самостоятельной, без ссылок на приватные файлы за его пределами.

При подготовке передачи используй только проект из `wordpress/`, без внутреннего репозитория и истории Git. Проверяй скрытые файлы, ссылки, секреты, приватные материалы и зависимости от внешних файлов. Основание: `docs/adr/0014-plugin-scoped-development-tools.md`.

# Локальные приватные наработки

Типографику и layout поддерживай по ADR-0021–0023 и документации темы. Используй локальные Ubuntu/Roboto 400/700, шкалу из документа типографики, H5–H6 со snug. Сохраняй defaultFontSizes: false, customFontSize: false, fluid: false; controls fontWeight/lineHeight/letterSpacing отключены. Layout: 1200/1600px, боковой padding через spacing 40, useRootPaddingAwareAlignments: true. Блоковые ограничения определяются отдельно.

Шкалу расстояний темы поддерживай по ADR-0019 и `wordpress/theme/docs/spacing.md`: пресеты `10–90`, для 50 — `1.5rem`, для 60 — `2rem`. Сохраняй `settings.spacing.defaultSpacingSizes: false`, `customSpacingSize: false` и `blockGap: true` согласно ADR-0020. Доступность padding/margin и настройки layout определяются отдельно.

В `theme.json` сохраняй `settings.color.defaultPalette: false` и `settings.color.custom: false`: стандартные controls цветов должны предлагать только палитру сайта. Не отключай controls текста и фона ради этого ограничения. Основание: `docs/adr/0018-site-palette-only.md`.

Цветовую систему темы поддерживай по ADR-0017 и `wordpress/theme/docs/colors.md`: `base` — основной фон, `contrast` — основной текст; ровно 10 принятых ролей палитры. При изменении значений обновляй документацию и проверяй контраст применяемых пар. При переносе остальных правил из наработок не используй обратную трактовку этих ролей. Основание: `docs/adr/0017-semantic-color-palette.md`.

Корневая папка `references/` содержит локальные приватные материалы владельца. Читай и ищи в ней только по его явному запросу для конкретной задачи. Исключай её из общего поиска, Git, архивов, передачи клиенту, публикаций и загрузок. Не используй `git add -f` для этих материалов. Использование отдельного решения не разрешает переносить весь исходник или приватные данные; копирование в отслеживаемые файлы допускается только в явно порученном объёме. Основание: `docs/adr/0015-local-private-references.md`.
