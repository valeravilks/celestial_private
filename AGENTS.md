По ADR-0059 небольшие вспомогательные подписи оформляй style variation caption блока core/paragraph на существующих токенах. Не заменяй семантический figcaption изображения обычным Paragraph. На тёмных поверхностях проверяй читаемость.

По ADR-0060 FAQ и аналогичные группы раскрывающегося содержимого создавай штатным core/accordion с item/heading/panel, а не набором Details или собственным переключателем. Уровень заголовков выбирай по структуре страницы; поведение сохраняй Core, оформление — в теме. Существующую библиотеку автоматически не переписывай.

По ADR-0057 при создании сайтов и секций выступай дизайнером: выбирай визуальное направление под задачу и самостоятельно предлагай подходящие фоны, изображения/видео, узоры, глубину и композиционные акценты. Не своди варианты к перестановке одинаковых карточек и не добавляй эффекты ради количества. Используй токены и оформление темы без включения controls; шкала теней, Shapes и ширины остаются отдельными открытыми вопросами. Это не поручение внедрять все эффекты сразу.

По ADR-0058 существенные новые композиции обосновывай просмотренными существующими примерами или одобренными элементами: сохраняй источник и конкретный заимствуемый приём, адаптируй к проекту. Перед показом самостоятельно оцени реальный рендер в браузере, композицию, медиа, контраст, действия, редактор и фактическую узкую ширину; исправь очевидные недостатки и проверь снова. Пустой скриншот или неприменившийся viewport не считай подтверждением. Большие подборки развивай после проверки репрезентативных примеров. Честно указывай незавершённые проверки; library не меняй автоматически.

По ADR-0056 запрос «создай сайт» трактуй по контексту бизнеса, а не как автоматический лендинг. Основной формат — многостраничный сайт; без подробностей выбирай консервативный полезный состав страниц. Явный список/формат владельца приоритетен. Если вопросы запрещены, самостоятельно выбери структуру и обозначь предположения. Обычные страницы — Pages, landing-page — отдельные лендинги по назначению. Принятие этого правила не разрешает сейчас перерабатывать мебельный тест.

По ADR-0054 целевой клиентский режим разрешает менять предусмотренное содержимое, сохраняя структуру блоков и секций готовой страницы. Для владельца сохраняй сценарий сборки. Не добавляй contentOnly механически и не полагайся на автоматическую блокировку WordPress; проверяй Enter, вставку, структурные операции и уровень страницы. Атрибут не является подтверждением полноценного клиентского режима. Разделение доступа пока не реализовано.

По ADR-0052 не удаляй ничего из library/ без точного подтверждения владельца. Перед удалением (включая прямой запрос) покажи точный список файлов/каталогов и последствия; дождись подтверждения. Перед изменением существующих library-файлов также покажи точный список и суть изменений, дождись подтверждения. Перезапись, переименование и перемещение входят в это правило. Запросы на изменения в wordpress/ не разрешают трогать library/. Уже подтверждённый точный список повторно не согласовывай; расширение списка согласуй отдельно. Создание новых записей по явному запросу разрешено по ADR-0045, но изменения существующих файлов требуют согласования списка.

По ADR-0051 новые и явно дорабатываемые секции с вводным блоком строй из корневой Group, отдельной Group Subtitle + заголовок и отдельной Group основного контента. Соблюдай: внутренний gap вводной группы < межгрупповой gap ≤ вертикальный padding секции (при разных верхнем/нижнем — меньший). Выбирай токены под композицию, проверяй fluid-значения на применяемых ширинах. Внутренние интервалы контента задавай отдельно. Старые patterns/library не исправляй автоматически; учитывай при обслуживании по ADR-0047.

По ADR-0047 при поручении обслуживания проверяй проект и все существующие элементы library/ по актуальным применимым ADR, независимо от даты создания. Фиксируй конкретные расхождения, влияние и предложения; старые проверки не подтверждают соответствие новым правилам. Не синхронизируй библиотеку автоматически, соблюдай ADR-0045 и явно разрешённый объём исправлений. Само сохранение этого правила не запускает аудит или фоновую работу.

По ADR-0046 в новых и адаптируемых patterns объединяй Subtitle и заголовок секции в отдельную Group. Внутренний gap должен быть меньше расстояния от группы до основного содержимого; используй токены композиции. В information-six-items выбраны spacing 20 внутри и spacing 50 снаружи. Не обновляй старые patterns или library автоматически.

По ADR-0045 сначала разрабатывай и проверяй новые элементы и изменения только в wordpress/. Не создавай и не обновляй реализации в library/ автоматически. Перенос из wordpress/ в library/ выполняй лишь по явному запросу владельца; при переносе обобщай контент, сохраняй зависимости и описывай выполненные проверки. Использовать существующую библиотеку для выбора разрешено.

По ADR-0044 в оформлении сайта выбирай только установленные иконки Lucide (lucide/<name>), вместо стандартной коллекции WordPress. Подбирай по смыслу действия, предмета или состояния блока; ищи в wordpress/plugin/includes/icons/assets/manifest.php и проверяй SVG. Подписи manifest краткие, не являются полными описаниями. Используй понятные и согласованные метафоры, не добавляй иконки без задачи, соблюдай доступность. При отсутствии подходящей иконки оставь текст или обсуди с владельцем; другой набор автоматически не подключай. Служебные иконки WordPress и старый контент это правило автоматически не заменяет.

Иконки Lucide встроены в wordpress/plugin/includes/icons по ADR-0042–0043. Используй core/icon и имена lucide/<name>; сохраняй готовые assets и лицензию в поставке. Не добавляй отдельный плагин, генератор или npm-зависимости и не включай controls дизайна. Обновления набора выполняются явно из готового релиза.

По ADR-0041 во всех templates используй общую Group с layout default и style.spacing.blockGap = "0". Страницы из полноширинных секций также оборачивай в Group с нулевым gap внутри Post Content. Не обнуляй внутренние интервалы секций глобально.

По ADR-0040 секции библиотеки и переиспользуемые patterns делай универсальными: нейтральные названия и подсказки, категории по назначению (например Benefits), без текстов текущего продукта, фиксированных якорей и ID сайта. Заполненный контент остаётся в странице проекта. celestial/ — технический namespace, а не продуктовая привязка.

# Работа с архитектурными решениями

Используй внутреннюю library/ по ADR-0037–0039: blocks/<block>/<style-variation>/<variant>/ и sections/<section>/. Называй subtitle style variation блока core/paragraph, dot/line — её библиотечными реализациями. Для проекта выбирай одну реализацию style variation со стабильным slug. Переноси в wordpress/ только необходимое, без runtime-зависимостей от библиотеки; фактический код проекта — источник истины. Не создавай Project Composition и не перезаписывай адаптированный код автоматическими обновлениями библиотеки. Клиентская документация описывает установленный результат; library/ не передаётся. Обычное пополнение библиотеки не требует нового ADR.

По ADR-0036 в wordpress/theme/templates/*.html разрешены только core/group и core/template-part на всех уровнях вложенности. Group задаёт композицию; допустима его соответствующая HTML-оболочка. Содержательные блоки и паттерны размещай в parts/*.html. Проверяй вложенные типы блоков, оболочки, существование частей по slug и отсутствие циклов; затем проверяй рендер. Пользовательские версии в базе данных учитывай отдельно.

Перед планированием и реализацией новой задачи прочитай `docs/project-goal.md` и оцени вклад в цель: готовый сайт по краткому запросу, понятный владельцу минимальный код, повторное использование, проверенное качество и самостоятельная сборка страниц. Если изменение не помогает цели или усложняет процесс без достаточной пользы, сообщи до реализации, объясни издержки и предложи более подходящий вариант. Не выдавай целевые возможности за уже реализованные. Делай первую рабочую версию в рамках принятых решений, задавая только существенные вопросы. Основание: `docs/adr/0033-goal-guided-development.md`.

Все собственные именованные глобальные PHP-функции темы и плагина называй с префиксом `celestial_` и понятным snake_case-именем. При добавлении, переносе и ревью проверяй префикс и уникальность имён между компонентами, включая callbacks хуков. При необходимости используй `celestial_theme_` или `celestial_plugin_`. Не маскируй дубли своих функций через function_exists. Методы, анонимные функции и внешние API этим правилом не переименовываются. Основание: `docs/adr/0029-function-prefix.md`.

Если владелец говорит «обсудим позже» или просит сохранить идею, добавь либо обнови карточку в `docs/questions/` и её реестр, предварительно проверив дубли. Не начинай реализацию отложенной темы. Возвращайся к ней по запросу владельца, сверяясь с действующими ADR. Поддерживай статусы и результат; принятый ADR не равен реализованному коду. Не создавай ADR на простое добавление вопроса. Основание: `docs/adr/0026-open-questions.md`.

После добавления ADR или изменения его статуса проверяй результат и создавай локальный Git-коммит с ADR и связанными изменениями задачи. Проверяй состав индекса; добавляй файлы явно, не захватывай несвязанные изменения пользователя и приватные материалы. Несколько связанных ADR одной задачи можно сохранять одним коммитом. Не выполняй push без отдельного указания. При невозможности коммита сообщи причину. Основание: `docs/adr/0016-commit-adr-changes.md`.

Самостоятельно разделяй запрос пользователя на отдельные ADR по независимым решениям, даже если они изложены одним сообщением. Решения, которые можно пересмотреть отдельно, оформляй отдельно; тесно связанные детали одного решения (например, пути каталогов и их назначение) объединяй. Не создавай ADR на каждую мелкую деталь. Основание: `docs/adr/0007-split-independent-decisions.md`.

Перед планированием и внесением изменений прочитай реестр `docs/adr/README.md` и действующие ADR, относящиеся к задаче. Заменённые ADR используй как исторический контекст, а не как действующие требования.

Сопоставь запрос пользователя и предлагаемые изменения с действующими решениями. Если обнаружено противоречие:

1. До замены ADR или реализации противоречащих изменений сообщи пользователю номера и названия затронутых ADR, существующие требования и суть противоречия.
2. Объясни предлагаемую замену и её последствия. По возможности предложи вариант, совместимый с текущими решениями.
3. Дождись явного подтверждения пользователя на замену конкретных решений. Общий запрос на новую функциональность сам по себе не означает согласия на пересмотр ADR. Если такое подтверждение уже получено после объяснения противоречия, повторно его не запрашивай.
4. После подтверждения оформи новый ADR, свяжи его с заменяемыми записями и обнови их статусы и реестр. Сохрани исходный контекст и текст прежних решений.

До подтверждения можно подготовить предложение со статусом «Предложено» и продолжать независимую работу, совместимую с действующими ADR. Изменения без противоречий выполняй без дополнительного согласования.

Основание: `docs/adr/0005-review-existing-decisions-before-replacement.md`.

# Граница передачи клиенту

Тема `wordpress/theme/` — основная FSE-тема Celestial для внешнего представления. Добавляй в неё только необходимое для оформления и работы FSE-темы. Не вводи сборку темы (в том числе из корня проекта), сборочные зависимости и генерируемые `build/` или `dist/`. Файлы темы используются WordPress напрямую. Функциональность, сохраняемая при смене темы, относится к плагину. Способ сборки плагина этим правилом не определяется. Основание: `docs/adr/0013-fse-theme-without-build.md`.

Вся разработка сайта ведётся внутри `wordpress/`. В корне этого каталога сохраняй `.wp-env.json`, компоненты и самостоятельную документацию. Не создавай там `package.json`, lock-файл, `.nvmrc` или локальные npm-зависимости. wp-env устанавливай глобально и запускай прямыми командами из `wordpress/`.

Инструменты сборки плагина находятся в `wordpress/plugin/`: @wordpress/scripts и npm-run-all, установка через npm ci, сборка npm run build, наблюдение npm run start. PHP-модули размещай в includes/<feature>/index.php с явными require_once; общие изменения редактора — editor/index.js; блоки — blocks/<block>/ с block.json. build/ и node_modules/ генерируются и исключены из Git; для поставки плагина build/ обязателен. Следуй ADR-0030–0032. У темы сборки нет.

Внутренние ADR, описание архитектуры, правила и приватные заметки процесса Celestial храни вне этого каталога. Документация внутри `wordpress/` должна быть самостоятельной, без ссылок на приватные файлы за его пределами.

При подготовке передачи используй только проект из `wordpress/`, без внутреннего репозитория и истории Git. Проверяй скрытые файлы, ссылки, секреты, приватные материалы и зависимости от внешних файлов. Основание: `docs/adr/0014-plugin-scoped-development-tools.md`.

# Локальные приватные наработки

Дополнительный готовый CSS Core-блоков подключай через celestial_theme_register_block_styles() и wp_enqueue_block_style на init по ADR-0028. Для каждой записи списка создай assets/blocks/<name>.css. Не путай подключение CSS с регистрацией style variation, не добавляй сборку темы; базовые свойства и токены оставляй в JSON. Гайд: wordpress/theme/docs/block-styles.md.

Сохраняй отключение core-block-patterns через after_setup_theme в wordpress/theme/functions.php согласно ADR-0027. Не удаляй собственные или пользовательские паттерны и не расширяй отключение на удалённый каталог без отдельного решения.





Цветовую систему темы поддерживай по ADR-0017 и `wordpress/theme/docs/colors.md`: `base` — основной фон, `contrast` — основной текст; ровно 10 принятых ролей палитры. При изменении значений обновляй документацию и проверяй контраст применяемых пар. При переносе остальных правил из наработок не используй обратную трактовку этих ролей. Основание: `docs/adr/0017-semantic-color-palette.md`.

Корневая папка `references/` содержит локальные приватные материалы владельца. Читай и ищи в ней только по его явному запросу для конкретной задачи. Исключай её из общего поиска, Git, архивов, передачи клиенту, публикаций и загрузок. Не используй `git add -f` для этих материалов. Использование отдельного решения не разрешает переносить весь исходник или приватные данные; копирование в отслеживаемые файлы допускается только в явно порученном объёме. Основание: `docs/adr/0015-local-private-references.md`.

# Общая политика дизайна редактора

Следуй ADR-0034: страницы собираются из готовых паттернов, стандартные controls дизайна скрыты глобально, включая padding и blockGap. Не вводи settings.blocks overrides. Сохраняй токены, шрифты, layout и общие стили темы; ограничения UI не должны удалять CSS дизайна. Общие списки семейств и размеров скрывает модуль плагина editor-policy. Не обещай полную невозможность изменения дизайна: сторонние controls, сохранённые атрибуты и права Site Editor требуют отдельных решений. Padding/gap пока не включать; их обсуждение остаётся в Q-0002.
