# Разработка темы и плагина

## Ответственность компонентов

Проект работает на WordPress с Gutenberg и собственной FSE-темой. `theme/` отвечает за представление: theme.json, templates, parts, patterns, готовые стили и ресурсы. Типы записей, данные, интеграции и функциональность, сохраняемая при смене темы, находятся в `plugin/`. Визуальный интерфейс блока не делает его автоматически частью темы.

Тема используется WordPress напрямую. Не добавлять сборку темы, npm-зависимости, генерируемые build/dist или сборку темы из родительского каталога. Инструменты Node.js находятся только в plugin/. В корне WordPress-проекта нет package.json, lock-файла, .nvmrc и node_modules; wp-env установлен глобально. [Запуск окружения](../README.md#локальная-разработка), [сборка плагина](../plugin/README.md#команды).

## Глобальные PHP-функции

Собственные именованные глобальные функции обоих компонентов используют `celestial_` в нижнем регистре и понятное snake_case-имя. Имена уникальны между темой и плагином; при необходимости уточнять `celestial_theme_` / `celestial_plugin_`.

При добавлении, переносе и ревью проверять префикс, уникальность и ссылки на функции, включая callbacks хуков. Не маскировать конфликт собственных имён через function_exists. Методы классов, анонимные функции и WordPress/сторонние API этим правилом не переименовываются.

## Функциональные модули

Создать `plugin/includes/<feature>/index.php`, закрыть прямой доступ проверкой ABSPATH и явно подключить require_once из celestial.php. Модуль подключает поведение через хуки WordPress. Не включать все файлы автоматически; не вводить классы только ради группировки хуков.

Модуль landing-pages регистрирует публичный landing-page с REST, title/editor/thumbnail, без архива. Политика sitemap и Dashboard отдельно не менялась. После изменения rewrite-правил обновить постоянные ссылки; окружение запускается из корня WordPress-проекта.

## Редактор и блоки

Общий код расширений Gutenberg — `plugin/editor/index.js`, сборка в build/editor. Подключение только в редакторе использует dependencies/version из index.asset.php; при отсутствии JS/asset-файла пропускается. Исходники блока — `plugin/blocks/<block>/block.json` и соседние JS/SCSS/PHP. CSS editor.scss относится к редактору, style.scss — к редактору и сайту.

Сборка через @wordpress/scripts и npm-run-all создаёт build/blocks и blocks-manifest.php. PHP регистрирует коллекцию на init, содержит fallback при отсутствии API; без манифеста регистрация пропускается. Сохраняется имя примера cel/example-static; общий namespace будущих блоков не выбирался отдельно. После изменения блоков выполнять сборку и проверять регистрацию, редактор и frontend. Изменение save статического блока может потребовать миграции сохранённых экземпляров.

build/ и node_modules/ генерируются и исключены из Git. Для установленного плагина build/ обязателен; node_modules на сервере не нужен. Версии и команды брать из package.json, lock-файла и .nvmrc плагина, а не из исторических примеров.

## Проверка результата

Для PHP проверять синтаксис, имена и применимый сценарий. Для шаблонов — [структуру частей](../theme/docs/templates.md). Для оформления — редактор, frontend и узкий экран. Учитывать сохранённые шаблоны и контент базы: изменение исходника не обновляет вставленный экземпляр автоматически. Честно указывать непроверенные сценарии.
