# ADR-0006: Документирование текущей архитектуры

- **Статус:** Принято
- **Дата:** 2026-10-13
- **Автор решения:** Владелец проекта

## Контекст

ADR сохраняют причины выбора технологий и историю изменений. Однако для понимания текущего устройства проекта приходится читать отдельные решения и учитывать, какие из них заменены. Нужен документ, в котором видны актуальные компоненты, инструменты и состояние их реализации.

Ранее отдельный Decision Log был удалён как дублирующий реестр ADR. Новый документ должен описывать систему, сохраняя ADR единственным механизмом принятия и фиксации архитектурных решений.

## Решение

Вести файл [`docs/architecture.md`](../architecture.md) с описанием текущей принятой архитектуры: назначение проекта, технологии и их роли, структура репозитория, компоненты и их взаимодействие по мере определения.

Для архитектурных выборов указывать ссылки на действующие ADR. Явно отличать принятый выбор от уже выполненной реализации и обозначать области, в которых решения ещё не приняты.

Обновлять документ при принятии или замене относящегося к нему ADR, а также при изменении состояния реализации. Причины, альтернативы, статусы решений и историю их пересмотра сохранять в ADR и реестре. Документ архитектуры отражает их результат и не вводит самостоятельных решений.

После появления файлов конфигурации проекта использовать их как источник конкретных версий зависимостей и настроек; в документе архитектуры давать ссылки на эти файлы.

Если описание расходится с действующим ADR, исправлять описание. Пересмотр самого решения проводить согласно ADR-0005.

## Альтернативы

- Хранить описание только в ADR: сохраняет историю, но требует собирать текущую картину из нескольких записей.
- Расширять только корневой README: возможно для небольшого проекта, но по мере развития смешивает краткое введение с подробностями архитектуры.
- Использовать полный шаблон архитектурной документации: сейчас достаточно одного файла, который можно расширять по мере появления компонентов.

## Последствия

- Текущая архитектура и набор инструментов доступны в одном документе.
- История и обоснования остаются в ADR; отдельный журнал решений не появляется.
- Документ необходимо поддерживать согласованным с действующими ADR и состоянием проекта.
- Неопределённые области видны явно, без преждевременного выбора инструментов.
